# v0.18 Implementation Plan

Status: planned.

v0.17 shipped Guided First Useful Almanac: first-use reports, natural-language
setup guidance, a concrete source checklist, abstention recovery guidance, and
guided first-answer promotion. A user can now go from an empty root to a
replayable first answer with far less command knowledge — as long as they are
willing to copy provider-backed commands out of Studio and run them in a
terminal with credentials.

That copy-paste seam is now the largest remaining gap between "a developer can
build an almanac" and "a domain expert can build an almanac". The expert who
owns the knowledge is rarely the person comfortable with `ANTHROPIC_API_KEY`
prefixes and CLI flags. Today they can see exactly what to do next in Studio,
but the two steps that matter most — compile and the first real answer — still
eject them to a terminal.

The theme for v0.18 is **Provider-Backed Studio**:

- let Studio run provider-backed compile and first-answer operations behind an
  explicit credential and confirmation boundary,
- let users supply their trusted references directly in Studio instead of
  hand-assembling a compile command,
- keep every provider call explicit, confirmed, bounded, and recorded as the
  same artifacts the CLI produces,
- keep Studio localhost-only, mutation-free on GET, and free of credential
  input or echo,
- preserve cite-or-abstain, freshness, artifact, and runtime contracts
  unchanged.

This resolves the v0.17 open decision: "whether a future release should allow
provider-backed Studio execution behind explicit confirmation and credential
boundary." The answer is yes, with the boundary defined in this plan.

## Target Users

v0.18 focuses on users who can describe their domain and identify trusted
references, but should not need a terminal to turn those into a working
almanac:

- domain experts who completed the v0.17 first-use checklist in Studio and
  stalled at the provider-backed compile handoff,
- users who have credentials available in their environment but do not want to
  compose CLI invocations by hand,
- personal users who want the first real answer in the same surface where they
  prepared the sources,
- technical evaluators who want to demo the full source-to-answer loop from one
  screen,
- existing CLI users who still want the CLI to remain the canonical, scriptable
  path — Studio execution must not fork behavior.

The target remains a local source-first product. Studio gains execution, not
hosting: no accounts, no remote access, no background service.

## Goals

- Define a provider readiness model: which credentials are present in the
  Studio server process environment, which operations they unlock, and which
  remain blocked — without ever echoing key material.
- Extend guided operations so provider-backed operations carry an explicit
  `providerBacked` boundary and a confirmation requirement, alongside the
  existing provider-free `studioRunnable` operations.
- Add a confirmation step for every provider-backed Studio execution that
  states what will run, which provider and model it will call, what it will
  write, and that it may incur cost — before anything executes.
- Run provider-backed compile from Studio with stage-level progress, the same
  saved run artifacts as the CLI, and failed-stage recovery rendered in place.
- Run the provider-backed first answer from Studio, rendering citations,
  freshness, and abstention recovery guidance with the same contracts as `ask`.
- Add reference intake to Studio: users submit trusted reference URLs against
  the v0.17 source checklist and see acceptance/rejection with next actions.
- Keep the CLI canonical: Studio execution must call the same code paths and
  produce the same artifacts, so runs remain auditable and replayable.
- Keep no-key demo and replay workflows working as deterministic smoke paths;
  every new Studio surface must degrade to explicit handoff when keys are
  absent.

## Scope

### Provider Readiness Model

Introduce a derived provider readiness report that can be rendered by
`doctor`, `status`, and Studio:

- which provider credentials are detected in the current process environment
  (presence only, never values or fragments),
- which guided operations each credential unlocks,
- which operations remain CLI handoff and why,
- embeddings and search credentials as optional capability flags.

Readiness is derived at request time from the server process environment.
Studio never accepts credential input from the browser and never persists
credentials to disk. Starting Studio with keys in the environment is the only
way to unlock provider-backed execution.

### Confirmation-Gated Execution

Extend the operation runner so provider-backed operations execute only when:

- the operation is requested by id over POST,
- provider readiness covers the operation,
- the request carries an explicit confirmation acknowledging the provider
  call,
- no other provider-backed operation is currently running for the same
  almanac.

The confirmation payload shown to the user must state the operation, the
provider boundary, the expected writes (run artifacts, almanac files), and
that the call may incur provider cost. Execution is bounded: one operation at
a time per almanac, no queues, no retries without a new confirmation.

### Studio Reference Intake

Let users complete the v0.17 source checklist inside Studio:

- submit candidate reference URLs against the checklist categories (official
  docs, repositories, secondary articles, community references),
- see accepted and rejected candidates with the same evaluator policy and
  user-facing reasons as the CLI,
- see the checklist flip to provider-ready when minimum viable sources are
  satisfied.

This reuses the existing source checklist and evaluator policy. It does not
add a general source editor, and it does not let Studio fetch or snapshot
content outside the compile pipeline's existing fetch stages.

### Provider-Backed Compile From Studio

Once the checklist is provider-ready and readiness covers compile:

- the compile operation becomes runnable from Studio behind confirmation,
- progress is rendered per pipeline stage while the run is active,
- success renders the same first-use report transitions as the CLI path,
- failure renders the failed stage and the existing resume guidance, with the
  resume operation runnable behind a fresh confirmation.

The Studio path must invoke the same compile pipeline entrypoint as the CLI
and save the same run artifacts. No Studio-only compile variant.

### Provider-Backed First Answer From Studio

After a successful compile:

- the first-question suggestions from the first-use report become runnable,
- a provider-backed ask runs behind confirmation and renders the answer with
  citations and freshness, or a valid abstention with the v0.17 recovery
  guidance,
- the saved answer artifact feeds the existing promotion flow (replay,
  fixtures, ask-suite, evidence save), which is already provider-free and
  Studio-runnable.

This closes the loop: reference intake, compile, first answer, and promotion
all reachable from one local screen, with the terminal needed only to launch
Studio with credentials.

## Non-goals

- No hosted dashboard, account system, cloud queue, or background worker.
- No credential entry, storage, or echo in Studio; environment detection only.
- No relaxation of localhost-only Studio binding.
- No mutation on Studio GET or page load.
- No arbitrary shell execution from Studio.
- No concurrent or queued provider-backed executions; one confirmed operation
  per almanac at a time.
- No browser-based full source/fact/fixture/artifact editor; reference intake
  is checklist-scoped.
- No new delivery surface (shared web UI, Slack bot) — candidate for a later
  release once provider-backed Studio is proven.
- No Studio-only execution semantics; the CLI remains canonical and Studio
  calls the same code paths.
- No replacement of the generic runtime boundary (`listTools`, `execTool`,
  `listResources`, `readResource`).
- No attempt to guarantee that every first answer is cited; valid abstention
  remains a successful safety outcome.
- No new hosted scheduler or resident daemon.

## Lessons From v0.17

- First-use reports work: users understand setup, checks, answer readiness,
  and first answer status without learning artifact names. Provider-backed
  Studio should extend that frame, not introduce a new one.
- The source checklist made compile-readiness legible, but satisfying it still
  requires composing a CLI command; the checklist is the natural place to
  accept references.
- Explicit provider boundaries built trust. Users accepted "this step needs
  credentials" when stated plainly — confirmation-gated execution is the
  continuation of that posture, not a departure.
- Abstention recovery guidance only pays off if the recovery operations are
  reachable where the abstention is rendered; Studio answers must render the
  same guidance.
- Operation-id based execution with result envelopes (v0.16) was the right
  base: provider-backed execution is an extension of the runner contract, not
  a new mechanism.
- Disposable roots under `/tmp` remain the right way to smoke mutating flows
  without touching managed almanacs.

## Product Shape

The v0.18 workflow should feel like this:

```bash
ANTHROPIC_API_KEY=... almanac studio
```

The user sees, in order, on one local screen:

- first-use state for the selected or new almanac,
- a source checklist that accepts pasted reference URLs and explains
  acceptance or rejection,
- a compile action that is blocked, handoff, or runnable depending on
  checklist and provider readiness — with an explicit confirmation before any
  provider call,
- stage-level compile progress, then the updated first-use report,
- suggested first questions, runnable behind confirmation, rendering a cited
  answer or a recoverable abstention,
- the existing provider-free promotion flow to make the first answer
  replayable and save readiness evidence.

Without credentials, every one of those steps renders the same copyable CLI
handoff as v0.17 — nothing regresses for the no-key path.

## Release Gate

v0.18.0 should not be cut until:

- source and linked CLI versions match,
- provider readiness reporting shows presence-only detection with no key
  material in any output or artifact,
- provider-backed operations are impossible to trigger without explicit
  confirmation, and double-submits are rejected,
- a Studio-run compile and a CLI compile of the same inputs produce equivalent
  run artifacts,
- the full Studio loop (intake → compile → first answer → promotion) passes
  with a mock provider in tests and with a real provider in RC smoke,
- the no-key path renders handoff at every provider step with no behavioral
  regression from v0.17,
- Studio remains localhost-only and GET/page load remains read-only,
- Enterprise AI still passes benchmark and real-provider ask/replay smoke when
  credentials are intentionally available.

## Decisions To Revisit

- Whether refresh runs should also become confirmable Studio operations, or
  stay CLI/scheduler-only for one more release.
- Whether compile progress should stream (SSE) or poll; start with polling
  unless implementation shows it is insufficient.
- Whether reference intake should later accept local file paths in addition to
  URLs, and under what snapshot policy.
- Whether a shared delivery surface (read-only web answers over the existing
  HTTP transport, or a Slack integration) becomes the v0.19 theme once
  provider-backed Studio is proven.
- Whether per-operation cost estimates should be shown in the confirmation
  step once usage reporting is reliable enough to be honest.
