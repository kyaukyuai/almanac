# v0.15 Implementation Plan

Status: shipped in v0.15.0 on 2026-06-04.

v0.14 made Almanac easier to approach: `almanac start` orients empty roots,
natural-language intake drafts a safe setup plan, guided vocabulary hides some
internal nouns, sqlite-demo can bootstrap answer readiness without keys, and
`almanac studio` gives users a local read-only dashboard.

The next gap is activation. Users can now see what Almanac is and what to do
next, but the product still asks them to stitch together the path from intent
to first useful answer. v0.15 should make that path explicit, measurable, and
hard to miss.

The shipped theme is **Guided Activation**:

- turn first-run orientation into activation milestones,
- let a natural-language goal become an explicit, reviewable create path,
- help users reach a first cited answer and saved replay artifact,
- show "what can I ask?" before users invent a question from scratch,
- make Studio a safer activation surface without becoming a full editor,
- preserve source-first, cite-or-abstain, freshness, provider-boundary, and
  artifact contracts.

## Target Users

v0.15 focuses on users who can accept a local CLI product but need fewer
conceptual decisions before the first success:

- personal users who want a working almanac for a real topic, not only the demo,
- users who can provide references but do not know the exact `new` command,
- users who want one guided path from setup to first answer,
- users who need suggested questions and visible next actions,
- users who trust a local dashboard more than CLI-only state,
- power users onboarding teammates into repeatable grounded answer workflows.

The target is not "hide everything forever". The target is "get users to the
first grounded answer, then reveal the durable model as needed".

## Goals

- Add an activation model that turns lifecycle state into explicit milestones:
  orient, prepare, compile, validate, ask, replay, maintain.
- Extend guided start so a natural-language goal can become an explicit create
  path when the user supplies references and confirms provider use.
- Make `almanac start` and `almanac status` show the next activation step for
  each almanac, not only health.
- Surface suggested questions and "what this almanac can answer" from existing
  profile/query-shape data.
- Add a first-answer path that makes saving, replaying, and promoting answer
  checks visible after a successful ask.
- Upgrade Studio from passive inventory to a guided activation dashboard with
  copyable commands and provider-free safe actions.
- Keep all provider-backed or mutating work explicit and reviewable.

## Non-goals

- No hosted SaaS, hosted account, cloud dashboard, or remote registry.
- No autonomous source ingestion from a vague prompt.
- No hidden provider calls from `start`, `status`, `doctor`, `maintain
  --dry-run`, or Studio page load.
- No full visual workflow builder.
- No browser-based source or fixture editor.
- No resident daemon, tray app, or background scheduler.
- No multi-user permissions, shared workspace, or hosted secret store.
- No relaxation of cite-or-abstain, freshness, or quality gates.
- No replacement of the generic runtime boundary (`listTools`, `execTool`,
  `listResources`, `readResource`).

## Lessons From v0.14

- `start` is the right entry point, but it still stops at "here is the next
  command" instead of measuring activation progress.
- Natural-language intake is safer as deterministic planning, but users need a
  clear handoff from plan to `new` when they are ready to spend provider tokens.
- Guided vocabulary helps, but it should be applied consistently to activation
  state: "references", "checks", "answer readiness", "history", and "next
  action" should appear together.
- sqlite-demo proves no-key answer readiness, but real activation requires the
  first saved answer artifact and replay pass for the user's own domain.
- Studio is valuable even as read-only. Its next step should be guided command
  and provider-free action surfaces, not artifact editing.
- Enterprise AI remains the credentialed release sample. sqlite-demo remains
  the no-key activation sample.

## Product Shape

The guided activation loop should fit this shape:

```bash
almanac start
almanac start "Build an almanac for production AI governance checks"
almanac start "Build an almanac for production AI governance checks" \
  --source https://www.nist.gov/itl/ai-risk-management-framework \
  --source https://owasp.org/www-project-top-10-for-large-language-model-applications/ \
  --apply
almanac status production-ai-governance-checks
almanac ask production-ai-governance-checks "What checks should happen before rollout?" --save
almanac ask-replay production-ai-governance-checks --from-runs
almanac maintain production-ai-governance-checks --dry-run
almanac studio
```

`almanac start` answers "where am I in activation?".

`almanac start "<goal>"` answers "what would Almanac create and what references
are needed?".

`almanac start "<goal>" --source ... --apply` answers "create the almanac now,
with explicit references and provider use".

`status`, `ask`, `ask-replay`, `maintain`, and `studio` should all reinforce
the same activation state instead of presenting disconnected commands.

## Activation Milestones

v0.15 should introduce a shared activation report. It can be derived from
existing lifecycle, profile, benchmark, ask readiness, and maintenance state;
it should not require a new compiled artifact.

Suggested milestones:

| Milestone | Meaning | Evidence |
| --- | --- | --- |
| `oriented` | user has a root, command surface, and next action | `start`/`doctor` inventory |
| `planned` | a goal has a slug, scope, references checklist, and provider boundary | natural-language intake output |
| `compiled` | almanac exists with completed compile or actionable recovery | compile state and manifest |
| `validated` | benchmark checks pass or explain what is missing | benchmark report |
| `answer-ready` | ask-suite or answer readiness says answers can be trusted | ask readiness report |
| `first-answer` | at least one saved answer artifact exists with citations or valid abstention | `.runs/answer-*.json` |
| `replayable` | saved answer replay passes without provider calls | ask-replay result |
| `maintainable` | maintenance dry-run has a clear provider-free/provider-required plan | maintain report |

Human surfaces should show the highest achieved milestone, the missing
milestone, and one copyable next command.

## Guided Create Contract

`almanac start "<goal>" --apply` should be explicit and conservative:

- require at least one `--source` unless a later release adds trusted source
  discovery confirmation,
- require provider credentials for compile paths that call providers,
- print the generated `almanac new` command before running or include it in
  JSON output,
- refuse to run when provider credentials are missing and show a no-key
  alternative,
- write no hidden plan file unless the user asks for a saved plan,
- reuse existing `new` pipeline behavior instead of creating a second compile
  path,
- preserve `--root`, `--slug`, `--profile`, `--depth`, `--scope`, and
  `--source` semantics.

This is not autonomous creation from a vague prompt. It is a guided wrapper
around the existing source-first creation command.

## First Answer Contract

The first answer path should make trust work visible:

- show suggested questions from profile/query shapes and available facts,
- encourage `ask --save` for the first real question,
- after a saved answer, print replay and fixture-promotion next actions,
- distinguish a valid abstention from a failed activation attempt,
- show citation count, stale citation count, unsupported claim count, and
  quality gate status in one compact block,
- avoid provider calls during replay and fixture validation.

The user should not have to know the phrase "answer artifact" before they can
save and replay one.

## Studio Activation Contract

Studio should remain local and bounded, but v0.15 can make it more useful:

- show activation milestones per almanac,
- show "recommended next action" with copyable command,
- show suggested questions for answer-ready almanacs,
- expose provider-free safe actions such as refresh status, ask-suite replay,
  maintenance dry-run, and inventory reload,
- avoid provider-backed actions unless the user explicitly starts them from
  copied CLI commands,
- avoid editing source files, fixtures, registrations, or artifacts.

If safe actions are added, they should be POST-only, localhost-only, explicit,
and covered by CLI-level tests. A copy-command-only implementation is an
acceptable first slice if action execution risks scope creep.

## Decisions For v0.15

- Studio stayed read-only and copy-command-oriented; provider-free action
  execution remains future work.
- Guided create uses rendered command output and immediate delegation, not
  saved plan files.
- Activation milestones are derived from existing artifacts instead of
  persisted as a new artifact.
- `start "<goal>" --apply` requires explicit `--source`; provider-backed source
  discovery from a vague prompt remains out of scope.
