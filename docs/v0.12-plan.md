# v0.12 Implementation Plan

Status: planned.

v0.11 made the first successful almanac path explicit: source-first install,
task-oriented `doctor`, no-key sqlite-demo handoff, saved answer replay, and
compile recovery guidance all work as a coherent onboarding path. v0.12 should
turn that first success into a repeatable local lifecycle for almanacs that
users keep, revisit, refresh, register, export, and eventually remove.

The planned theme is **Installed Almanac Lifecycle**:

- make every installed almanac discoverable from a root,
- show whether each almanac is usable, stale, broken, registered, or needs
  validation,
- make import/export/wiki handoff feel like one lifecycle instead of separate
  utility commands,
- expose registration drift and cleanup actions before users run host clients,
- keep all lifecycle checks local-first and provider-free by default.

## Goals

- Upgrade `almanac list` from a compact inventory into a useful lifecycle
  dashboard across the root.
- Add a concise per-almanac lifecycle status view that combines compile health,
  facts/tools, benchmark, answer readiness, refresh due state, saved runs,
  registration state, and next actions.
- Define a safe import path for exported almanac archives, including collision
  policy, manifest validation, and post-import inspection guidance.
- Make client registration state visible and repairable, including stale MCP
  entries and Skill adapter mismatches.
- Improve root hygiene: detect broken directories, partial almanacs, orphaned
  registrations, and cleanup opportunities without destructive defaults.
- Preserve the no-key sqlite-demo path as the local golden sample and keep
  Enterprise AI as the credentialed release sample.

## Non-goals

- No hosted account, hosted registry, or marketplace.
- No resident daemon or automatic background refresh scheduler.
- No automatic refresh before `ask`.
- No multi-turn chat memory, personal-memory graph, or note-taking UI.
- No broad web UI or dashboard server.
- No package registry publishing work.
- No mandatory embeddings, mandatory judge, or hidden provider calls from
  lifecycle commands.
- No replacement of `inspect`, `profile`, `doctor`, `runs`, `refresh`, or
  `register`; v0.12 should compose and harden them before inventing large new
  surfaces.

## Lessons From v0.11

- The first-run path is now good enough to hand to another operator, but it
  stops at "you made one almanac." Personal use needs "what do I have
  installed, what is healthy, and what should I do next?"
- `almanac list` already exists, but it mostly shows identity and counts. It
  does not yet answer whether an almanac is valid, benchmarked, answer-ready,
  refresh-due, or registered.
- `inspect`, `profile`, `doctor`, `refresh due`, `runs`, and `register` each
  know part of the lifecycle. v0.12 should reuse those checks rather than
  duplicating another readiness model.
- `remove` already has dry-run-by-default behavior and registration cleanup.
  That is a good safety precedent for import, repair, and root cleanup.
- The committed sqlite-demo wiki snapshot is a strong documentation asset, but
  the CLI does not yet have a symmetric "import this handoff and inspect it"
  workflow.

## Product Shape

The lifecycle should fit the way a personal user thinks:

```bash
almanac list
almanac status sqlite-demo
almanac refresh due sqlite-demo
almanac ask-suite sqlite-demo
almanac export sqlite-demo
almanac import ./sqlite-demo.tar.gz
almanac register sqlite-demo --client=claude-code --apply
almanac remove sqlite-demo
```

`list` answers "what do I have?".

`status` answers "can I use this right now, and what should I do next?".

`import` answers "can I install a portable almanac someone handed me?".

Registration visibility answers "will my host client load the same almanac I
just inspected?".

## Lifecycle Status Model

v0.12 should avoid inventing another opaque health score. Prefer a small set
of task-oriented status fields that can be displayed in `list --json`,
`status --json`, and human output:

- `compile`: `ok`, `attention`, `failed`, or `missing`,
- `knowledge`: fact count, tool count, retrieval mode, and index presence,
- `benchmark`: passed/failed/missing and fixture coverage,
- `answer`: ready/needs-validation/missing with last suite or replay status,
- `refresh`: due/not-due/unknown, stale fact count, and last refresh artifact,
- `registration`: current/stale/missing/unknown per supported client,
- `runs`: latest saved run/answer/refresh artifact and retention hints,
- `handoff`: export/wiki/import-readiness hints,
- `nextActions`: concrete commands, ordered by unblock value.

Human output should stay compact. JSON output should be stable enough for CI
and shell automation.

### PR5: Import Handoff

Acceptance:

- Import validates manifest, directory shape, and unsafe paths before writing.

- Import output recommends `almanac status <id>` and `almanac benchmark <id>`.
- No provider credentials are required.

4. `status sqlite-demo` human and JSON output,
5. benchmark, saved answer replay, and `ask-suite`,
6. refresh due and latest run/answer/refresh visibility,
7. export/import round trip into a second fresh root,

11. Enterprise AI fresh compile/update smoke,
12. Enterprise AI real-provider ask, saved replay, and ask-suite smoke.

Provider-backed items should remain clearly separated from no-key lifecycle
items.

## Open Questions

- Should `almanac status <id>` be a new command, or should `inspect` grow a
  `--summary` mode? The current plan favors a new command because `inspect`
  already serves detailed artifact review.
- Should import support renaming with `--as <id>` in v0.12, or should it start
  with strict manifest ids and add renaming later?
- Should registration visibility live under `register --status`, `status`, or
  both? The plan favors both: `status` summarizes, `register --status` drills
  into client-specific details.
- How much root cleanup should be automated versus reported as explicit
  commands? v0.12 should default to reporting and dry-run cleanup only.
