# v0.14 Implementation Plan

Status: shipped in v0.14.0 on 2026-06-04.

v0.13 made a compiled almanac maintainable: users can dry-run and apply
maintenance, preserve maintenance evidence, preview repairs and cleanup, and
generate scheduler handoff snippets. The next product gap is not another deep
runtime capability. It is the first-run experience for users who do not want to
learn the internal model before seeing value.

The shipped theme is **First-Run Guided Experience**:

- let no-code-oriented users start with one command,
- accept a natural-language goal before exposing compile details,
- explain state with user-facing language instead of implementation nouns,
- bootstrap answer readiness without provider credentials where possible,
- give GUI-dependent users a local read-only dashboard for confidence,
- preserve the source-first, cite-or-abstain, provider-boundary, and artifact
  contracts under the simpler surface.

## Target Users

v0.14 focuses on users who are currently underserved by the CLI-first product:

- users who want to try Almanac without choosing subcommands,
- users who expect to describe their goal in natural language first,
- users who do not want to learn `sources`, `facts`, `fixtures`, and
  `artifacts` before the first success,
- users who are uncomfortable trusting a CLI-only status surface,
- power users onboarding teammates or non-specialist collaborators.

Power-user commands should remain intact. v0.14 should add a guided entry layer,
not replace the lower-level workflow.

## Goals

- Add `almanac start` as a guided first-run command that can route users to
  demo, existing almanac status, or new almanac creation.
- Add `almanac start "<goal>"` as a natural-language intake path that drafts a
  scope, source checklist, and first actions before running provider-backed
  work.
- Introduce a user-facing vocabulary layer for status/profile/maintenance copy:
  references, extracted knowledge, checks, history, and health instead of only
  sources, facts, fixtures, artifacts, and benchmark.
- Make answer readiness easier to bootstrap in no-key flows with deterministic
  ask fixture seeding for demo/sample almanacs.
- Add a local read-only `almanac studio` dashboard that shows installed
  almanacs, health, references, checks, latest runs, latest answers, and the
  next best action.
- Keep all mutating or provider-backed actions explicit. Guided flows may draft
  and explain, but they should not silently ingest sources, spend provider
  tokens, register clients, or delete artifacts.

## Non-goals

- No hosted SaaS, hosted account, hosted scheduler, or remote registry.
- No multi-user permissions, shared secret store, or team administration.
- No full workflow-builder GUI.
- No write-heavy GUI for editing compiled artifacts.
- No hidden autonomous source ingestion from natural-language prompts.
- No automatic provider call from read-only `status`, `doctor`,
  `maintain --dry-run`, or `studio`.
- No resident daemon or background tray app.
- No replacement of the generic runtime boundary (`listTools`, `execTool`,
  `listResources`, `readResource`).
- No attempt to hide citations, abstentions, freshness, or provider
  requirements when they matter.

## Lessons From v0.13

- Maintenance is useful once an almanac exists, but the product still expects
  users to know which first command to run.
- `status`, `profile`, and `maintain` are accurate, but the vocabulary still
  exposes internal concepts before users understand the product.
- sqlite-demo proves no-key validation is possible, but answer readiness still
  needs a smoother bootstrap. A mock `ask --save` artifact without tool calls is
  correctly rejected by `ask-fixtures add-from-run`, but the user needs a
  deterministic happy path.
- Scheduler handoff showed the right pattern: generate caller-owned snippets
  without installing infrastructure. `studio` should follow the same posture:
  local, explicit, and disposable.
- Enterprise AI remains the credentialed release sample; sqlite-demo should
  remain the no-key guided onboarding sample.

## Product Shape

The first-run loop should fit this shape:

```bash
almanac start
almanac start "Build an almanac for production AI governance checks"
almanac studio
```

`almanac start` answers "what should I do first?".

`almanac start "<goal>"` answers "can Almanac draft a safe setup plan from my
intent?".

`almanac studio` answers "what do I have, is it healthy, and what is the next
best action?".

The lower-level commands remain available and should be shown as copyable
details:

```bash
almanac demo
almanac status <id>
almanac maintain <id> --dry-run
almanac ask-fixtures init <id>
almanac ask-suite <id>
```

## User-Facing Vocabulary

v0.14 should present a softer vocabulary at the guided layer:

| Internal term | Guided term | Meaning shown to users |
| --- | --- | --- |
| sources | references | URLs, repos, docs, or files Almanac can cite |
| facts | extracted knowledge | grounded snippets available to tools and answers |
| benchmark fixtures | checks | deterministic validations for compiled tools |
| ask fixtures | answer checks | replayable answer-mode validations |
| artifacts | history | saved runs, answers, maintenance, exports |
| freshness | freshness | keep this term; it is product-critical |
| abstention | abstention | keep this term, but explain as "refused without enough support" |

This vocabulary should not change on-disk formats. It is a presentation layer
for first-run and dashboard surfaces.

## Guided Start Contract

`almanac start` should be provider-free by default:

- if no almanacs exist, offer demo first and show the command it will run,
- if almanacs exist, show a compact inventory and next best action,
- if provider keys are missing, explain which paths are still available,
- if provider keys are present, offer a new-almanac path but require explicit
  confirmation before provider-backed compile starts,
- if the user supplies a natural-language goal, draft scope and source needs
  without mutating until confirmed.

The first implementation can be non-interactive-friendly:

- human output for terminals,
- `--json` for tests and future UI,
- flags for `--demo`, `--dry-run`, and `--yes` where appropriate.

## Local Studio Contract

`almanac studio` should start as a read-only local dashboard:

- bind to localhost only,
- show the selected root and installed almanacs,
- show health, references, checks, answer readiness, refresh status,
  registration status, latest history, and next best action,
- link or copy exact CLI commands for mutating actions,
- avoid editing source files, fixtures, registrations, or artifacts in v0.14,
- run without provider credentials.

The first version can be intentionally plain. Its value is confidence and
orientation, not a rich hosted interface.

## Decisions For v0.14

- `almanac start` stayed non-interactive and copy-paste oriented.
- `almanac studio` shipped under `src/manage/` as a management surface.
- Seeded answer checks were scoped to sqlite-demo for v0.14.
- Natural-language intake stayed deterministic and provider-free; it prints
  provider-backed commands instead of calling providers.
