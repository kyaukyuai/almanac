# v0.11 Implementation Plan

Status: planned.

v0.10 made answer trust and compile stability observable: deterministic replay
and default `ask-suite` stayed provider-free, optional entailment judging found
unsupported or uncertain claims, source/fixture stability diagnostics became
auditable, and retrieval readiness stopped treating missing optional embeddings
as a product failure. v0.11 should use that operational depth to make the
product easier to start using.

The planned theme is **Install + First Successful Almanac**:

- make the source-first install path reliable and easy to verify,
- give first-run users one clear no-key success path before real provider work,
- explain readiness for demo, real compile, answer mode, and registration,
- improve failure recovery when provider, source discovery, or benchmark stages
  halt a real compile,
- preserve the local-first, artifact-first product shape.

See GitHub issue #71 for the v0.10.0 post-release verification snapshot and the
v0.11 seeds that motivated this plan.

## Goals

- Make package/bin sanity explicit enough that a user can verify the CLI from a
  fresh clone, linked install, and one-off `bun src/cli.ts` invocation.
- Improve first-run `doctor` and docs so operators can tell whether they are
  ready for offline demo, real compile, answer mode, optional judge, refresh,
  and client registration.
- Make the offline demo path feel like the canonical first success, not just a
  test fixture.
- Add or document a reviewable sample-almanac handoff path so users can inspect
  a useful artifact before spending provider tokens on a fresh compile.
- Improve interrupted/failed compile recovery messages with exact next commands,
  provider timeout guidance, and artifact locations.
- Run a release-candidate smoke from a clean checkout that proves first install,
  first demo, first real compile, first ask, replay, and recovery guidance.

## Non-goals

- No hosted service, hosted refresh scheduler, or resident daemon.
- No marketplace, package registry launch, or paid distribution channel.
- No broad UI application.
- No multi-turn chat memory or personal-memory graph.
- No automatic refresh before answering.
- No mandatory embeddings or mandatory entailment judge.
- No change to the core runtime boundary: MCP, CLI run, answer mode, benchmark,
  refresh, and Skill adapters continue to invoke compiled tools through the
  generic runtime contract.
- No attempt to eliminate all LLM/source non-determinism in v0.11; this release
  should improve diagnosis and recovery, while deeper source pinning can remain
  a later compile-stability project.

## Lessons From v0.10

The v0.10 release cycle left the product in a strong but operator-heavy state:

- The release/tag/notes flow is now reliable, but the project is still
  source-first. Users need a crisp "from clone to first success" path.
- The optional entailment judge did its job by finding one unsupported and one
  uncertain claim in a promoted Enterprise AI answer. That should seed answer
  quality improvements, but it should not make provider-backed judging a hidden
  default.
- `doctor` and `profile` now expose answer and retrieval readiness. v0.11
  should organize those checks around a first-run user's actual question:
  "What can I successfully do right now?"
- Enterprise AI RC smoke can pass, but a real compile still takes provider
  credentials, time, network access, and occasional retry. Recovery instructions
  need to be first-class product output.
- The offline sqlite demo is the best onboarding asset. It should become the
  entry point for evaluating run artifacts, answer replay, refresh validation,
  export, wiki output, and client registration without keys.

## Product Shape

The first successful workflow should fit on one screen:

```bash
git clone https://github.com/kyaukyuai/almanac.git
cd almanac
bun install
bun src/cli.ts doctor

tmp="$(mktemp -d)"
bun src/cli.ts demo --root "$tmp"
bun src/cli.ts inspect sqlite-demo --root "$tmp"
bun src/cli.ts profile sqlite-demo --root "$tmp"
bun src/cli.ts benchmark sqlite-demo --root "$tmp"
bun src/cli.ts run sqlite-demo \
  --tool query_facts \
  --input '{"q":"transactions atomic"}' \
  --root "$tmp"
```

After that succeeds, the user should have clear next paths:

- link the local CLI with `bun link`,
- save and replay a demo answer,
- export or wiki the demo artifact,
- register the demo with a client,
- run a real provider-backed compile only after `doctor` says the environment
  is ready.

## First-Run Readiness

`doctor` already reports runtime, credentials, optional embeddings, and almanac
artifact health. v0.11 should make this more task-oriented.

Recommended readiness buckets:

- `demo`: Bun available, repo dependencies installed, writable root available,
- `real-compile`: `ANTHROPIC_API_KEY` present, optional discovery credentials
  described, required local tools available,
- `answer`: compiled almanac present, benchmark passed, answer fixtures or
  latest answer evidence status visible,
- `judge`: provider configured explicitly for opt-in entailment judging,
- `registration`: target client paths and write permissions understandable,
- `refresh`: freshness state, locks, benchmark status, and ask-suite status
  visible.

Output should prefer exact commands over prose. For example, when no real
provider key is present, recommend `almanac demo` before `almanac new`.

## Install And Bin Sanity

The project remains source-first in v0.11, but the source-first experience
should be testable:

- verify `bun src/cli.ts --version` from the repository root,
- verify `bun link` exposes `almanac --version`,
- verify linked `almanac` works from outside the repository,
- keep `package.json` bin metadata and CLI shebang behavior covered by tests or
  smoke scripts,
- document how to recover when `almanac` resolves to an old linked checkout.

This does not require publishing to npm in v0.11. The goal is to make the
current installation model dependable before adding distribution channels.

## Sample Almanac Handoff

The demo command is a generator, but users may also benefit from an inspection
artifact they can review without compiling anything.

Candidate deliverables:

- a documented `almanac export sqlite-demo` flow as part of first-run docs,
- a small sample wiki export committed or generated during smoke,
- an optional checked-in fixture bundle for docs/tests if it stays small and
  license-safe,
- clearer docs showing what files a compiled almanac contains and which files
  are safe to share.

Avoid committing large generated archives unless there is a strong maintenance
reason. The first pass can be documentation and smoke coverage over existing
export/wiki commands.

## Compile Failure Recovery

Real compiles can fail for provider timeouts, source fetch problems, schema
validation retries, or benchmark fixture generation. v0.11 should make the
halt state easier to act on.

Recommended improvements:

- show the exact `almanac update --from-stage ... --no-bump` command for the
  first failed stage,
- point to `.compile/compile-state.json` and the most relevant stage artifact,
- distinguish provider timeout, provider schema failure, network source
  failure, benchmark coverage failure, and deterministic runtime failure,
- preserve the existing partial artifacts so users can inspect what succeeded,
- ensure `inspect`, `profile`, and `doctor` agree on next actions.

The goal is not to make every compile succeed automatically. The goal is that a
failed compile should still teach the operator what to do next.

## Open Questions

- Should v0.11 add a dedicated `doctor --first-run` mode, or should the default
  `doctor` output become task-oriented enough without a new flag?
- Should sample artifacts be generated in smoke only, or should a tiny
  committed sample manifest exist for docs?
- How much linked-bin behavior should be covered by automated tests versus
  release smoke, given `bun link` mutates user-level state?
- Should compile failure recovery stay as CLI text improvements, or should
  stage failure records gain a structured `recommendedCommand` field for JSON
  consumers?
