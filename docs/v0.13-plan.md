# v0.13 Implementation Plan

Status: shipped in v0.13.0 on 2026-06-04.

v0.12 turned a compiled almanac into an installed local asset: users can list
it, inspect status, import a handoff, see registration drift, diagnose root
hygiene, and remove it safely. v0.13 should make that asset maintainable over
time. The product should answer "what should I run today?" and "what will this
change?" without making users stitch together `status`, `refresh`, `benchmark`,
`ask-suite`, `runs`, `doctor`, `register`, and cleanup commands by hand.

The planned theme is **Personal Almanac Maintenance**:

- summarize whether each installed almanac is safe to use today,
- plan and run due maintenance with dry-run visibility,
- keep benchmark and ask-mode quality checks attached to refresh routines,
- turn doctor/status findings into explicit repair or cleanup candidates,
- make scheduler handoff copy-pasteable without introducing a resident daemon,
- help users promote, audit, and prune answer fixtures safely.

## Goals

- Add a maintenance report model that combines refresh due state, benchmark
  freshness, ask-suite status, latest answer quality, registration drift,
  cleanup candidates, and concrete next actions.
- Add a manual maintenance runner for one almanac or all almanacs, with
  dry-run first behavior and an apply mode for due refresh/validation work.
- Integrate benchmark and ask-suite validation into maintenance so users can
  keep answer mode ready after source refreshes.
- Add repair and cleanup audit surfaces that make existing `doctor`, `status`,
  `register`, `runs`, and `remove` findings actionable without hidden
  destructive defaults.
- Provide scheduler handoff output for cron, launchd, and GitHub Actions so
  personal users can run maintenance routinely with their own operating system
  or CI.
- Improve answer fixture maintenance: detect non-replayable saved answers,
  duplicate fixtures, stale fixture evidence, missing coverage, and promotion
  candidates.
- Preserve the v0.12 local-first contract: no hidden provider calls from status
  or dry-run maintenance, no background daemon requirement, and no automatic
  repair without explicit apply.

## Non-goals

- No hosted account, hosted scheduler, registry, marketplace, or team
  administration surface.
- No resident daemon, tray app, or always-on background process.
- No automatic refresh before every `ask`.
- No broad web dashboard.
- No package registry publishing work.
- No multi-user access control, shared credentials, or remote secret storage.
- No mandatory embeddings or mandatory LLM judge.
- No destructive cleanup or registration rewrite without an explicit
  `--apply` or equivalent confirmation flag.
- No attempt to make real-provider compile fully deterministic; v0.13 should
  surface and contain provider variance rather than pretending it vanished.

## Lessons From v0.12

- Lifecycle visibility is now good, but it still stops at "here is the
  condition." A personal user needs "here is the maintenance plan, and here is
  the safe command to apply it."
- `status`, `doctor`, `refresh due`, `benchmark`, `ask-suite`, `runs`,
  `register --status`, and cleanup guidance already know most of the required
  facts. v0.13 should compose them into a maintenance plan rather than
  inventing another health model.
- Root hygiene should stay conservative. The current dry-run posture is right;
  v0.13 can add repair/cleanup commands, but they must explain exactly what
  would change before writing.
- Answer readiness is practical once a fixture exists, but users still need to
  understand when a saved answer is replayable. The v0.12 abstention promotion
  fix should become a first-class audit result.
- Scheduler documentation exists, but personal use needs generated command
  snippets and environment checklists tailored to the selected almanac/root.
- Enterprise AI remains a strong credentialed release sample, but v0.13 should
  keep sqlite-demo as the no-key golden maintenance sample.

## Product Shape

The maintenance loop should fit a weekly personal workflow:

```bash
almanac maintain sqlite-demo --dry-run
almanac maintain sqlite-demo --apply
almanac maintain --all --due-only --dry-run
almanac maintain --all --due-only --apply

almanac repair sqlite-demo --dry-run
almanac cleanup --dry-run

almanac schedule print sqlite-demo --target launchd
almanac schedule print sqlite-demo --target cron
almanac schedule print sqlite-demo --target github-actions

almanac ask-fixtures init sqlite-demo
almanac ask-fixtures add-from-run sqlite-demo <answer-id>
```

`maintain --dry-run` answers "what would be refreshed, validated, or cleaned
up?".

`maintain --apply` answers "run the safe due work now and save the evidence.".

`repair --dry-run` answers "which broken links or registrations can be fixed?".

`schedule print` answers "how do I run this periodically outside Almanac?".

`ask-fixtures init/add-from-run` answers "which saved answer did I explicitly
promote into my replay set?".

## Maintenance Report Model

The report should be available in human and JSON output and should stay stable
enough for shell automation:

- `almanacId`, `version`, `root`, and checked timestamp,
- `status`: `ready`, `due`, `needs-validation`, `repairable`, `blocked`, or
  `broken`,
- `refresh`: due decision, overdue state, recommended from-stage, and last
  refresh artifact,
- `benchmark`: latest status, age, coverage counts, and whether rerun is
  planned,
- `answer`: latest answer, ask-suite status, fixture count, quality status,
  stale/unsupported/abstention mismatch counts,
- `registration`: current/stale/missing summary by client,
- `artifacts`: old runs, compile artifacts, exports, and cleanup candidates,
- `repairs`: explicit repair candidates with command, risk, and apply flag,
- `plan`: ordered maintenance steps with reason, command, provider requirement,
  and expected artifact,
- `result`: when applied, step outcomes and saved run artifact paths.

Dry-run output should never mutate. Apply output should save a maintenance
artifact under `.runs/` so later `status`, `runs`, `profile`, and `doctor` can
explain what happened.

### PR2: Maintenance Report Model

Add a provider-free maintenance report builder and expose it in dry-run output.

Likely touch points:

- new maintenance report types/schema,
- readers for lifecycle status, refresh due, benchmark report, ask-suite
  artifacts, latest answer, registration status, and root hygiene,

- `almanac maintain <id> --json --dry-run` emits stable report fields.

### PR3: Due-Only Maintenance Runner

Run the safe due work for one almanac or a root of almanacs.

Likely touch points:

- `almanac maintain <id> --apply`,
- `almanac maintain --all --due-only --apply`,
- refresh due integration,
- benchmark rerun after refresh,
- maintenance run artifacts under `.runs/`,
- lock behavior shared with refresh runs.

Acceptance:

- Dry-run and apply plans match except for timestamps/artifact ids.
- `--due-only` skips not-due almanacs with a clear reason.
- Applied maintenance saves an artifact with step results, benchmark summary,
  and next action.
- Failed refresh/benchmark steps are recorded without hiding partial progress.
- No provider credentials are required unless the selected from-stage requires
  provider-backed compile stages.

Validation:

- due/not-due fixture tests,
- lock conflict tests,
- sqlite-demo maintain apply smoke,
- `bun run typecheck`,
- `bun test`.

### PR4: Ask-Suite Maintenance Integration

Attach answer validation to maintenance routines.

Likely touch points:

- `maintain --ask-suite` or default ask-suite behavior when fixtures exist,
- ask-suite result embedding in maintenance artifacts,
- status/profile/doctor latest maintenance visibility,

Acceptance:

- If ask fixtures exist, maintenance can run provider-free ask-suite after

- Ask-suite failure marks maintenance attention without corrupting compile or

- Unsupported claim, stale citation, and abstention mismatch counts are visible

Validation:

### PR5: Repair And Cleanup Audit

Turn doctor/status findings into explicit repair and cleanup candidates.

Likely touch points:

- `almanac repair <id> --dry-run`,
- `almanac repair <id> --apply` for low-risk repairs,
- `almanac cleanup --dry-run`,
- integration with registration status, stale manifest counts, missing generated
  docs, orphaned registrations, old run artifacts, and removable broken
  directories.

Acceptance:

- Repair/cleanup output lists exact paths and commands before mutation.
- Apply mode is explicit and limited to low-risk, reversible, or regenerable
  changes.
- Registration repair reuses existing `register --apply` semantics where
  possible.
- Cleanup never deletes a compiled almanac without going through explicit
  remove behavior.

Validation:

- dry-run/apply repair fixture tests,
- root cleanup fixture tests,
- registration repair smoke with temporary client configs,
- `bun run typecheck`,
- `bun test`.

### PR6: Scheduler Handoff

Generate scheduler snippets that run maintenance outside Almanac.

Likely touch points:

- `almanac schedule print <id> --target launchd|cron|github-actions`,
- root/path/env rendering,
- docs for credential and log expectations,
- validation that snippets use `maintain --due-only` or the chosen safe mode.

Acceptance:

- launchd, cron, and GitHub Actions snippets are copy-pasteable.
- Output includes the root path, almanac id, recommended command, environment
  checklist, log path, and how to inspect the latest maintenance run.
- No scheduler is installed automatically in v0.13.
- The generated command defaults to dry-run or due-only unless the user
  explicitly requests an apply snippet.

Validation:

- snapshot tests for every target,
- docs examples,
- `bun run typecheck`,
- `bun test`.

### PR7: Answer Fixture Maintenance

Make saved answer promotion and fixture health safer for personal use.

Likely touch points:

- `almanac ask-fixtures init <id>`,
- `almanac ask-fixtures add-from-run <id> <answer-id>`,
- duplicate fixture detection,
- non-replayable abstention detection,
- stale citation and missing evidence warnings,
- fixture pruning guidance if a safe command shape is available.

Acceptance:

- Users explicitly select which saved answer to promote.
- Correct abstentions with cited tool evidence are reported as saved-run replay

- Non-replayable abstentions are rejected before they enter fixture JSONL.
- Promotion remains explicit and reviewable.

Validation:

## Open Questions

- Should `maintain --apply` run ask-suite by default when fixtures exist, or
  require `--ask-suite` until users trust the routine?
- Should repair live under `almanac repair`, or should low-risk repairs remain
  attached to existing commands such as `register --apply`, `resume`, and
  `runs --prune`?
- Should scheduler snippets default to dry-run, due-only apply, or ask the user
  to choose with an explicit flag?
- How much fixture pruning should be automated versus reported as reviewable
  JSONL edits?
- Should maintenance reports become the eventual hosted/dashboard API shape, or
  stay a CLI-only local artifact for now?
