# v0.10 Implementation Plan

Status: planned.

v0.9 made answer mode operational: saved answers can become fixtures,
`ask-suite` can run deterministic replay gates, refreshes can record ask-suite
validation, and doctor/profile can explain answer readiness. v0.10 should make
that workflow more trustworthy for repeated personal use by adding semantic
answer validation, reducing compile-time variance, and making retrieval
readiness explicit.

The planned theme is **answer trust and compile stability**:

- add an optional entailment judge for cited answers,
- keep deterministic replay as the default gate,
- make source discovery and benchmark generation easier to stabilize,
- surface retrieval mode and semantic-search readiness clearly,
- preserve the source-first, local-first product shape.

## Goals

- Add an opt-in answer entailment judge that checks whether cited evidence
  supports generated answer claims.
- Make judge output auditable in saved answer, replay, and suite artifacts.
- Keep `ask-suite` deterministic by default and provider-free unless a judge is
  explicitly requested.
- Improve compile stability controls around source reuse, source-set drift, and
  Stage 11 fixture repair feedback.
- Make retrieval defaults and readiness understandable from `doctor`,
  `profile`, and docs.
- Run a release-candidate smoke that covers sqlite-demo, Enterprise AI, real
  provider ask, saved replay, ask-suite, optional judge validation, and refresh
  integration.

## Non-goals

- No mandatory LLM judge.
- No hidden provider calls from `doctor`, `profile`, deterministic replay, or
  default `ask-suite`.
- No multi-turn chat memory.
- No hosted scheduler or resident daemon.
- No marketplace or package publishing work.
- No change to the core runtime boundary: compiled tools remain invoked through
  the generic runtime contract.
- No automatic refresh before answering.
- No replacement of Stage 11/12 benchmarks with ask-mode fixtures.

## Lessons From v0.9

v0.9 moved answer validation from ad hoc smoke to maintained fixtures, but the
release cycle exposed the next set of product gaps:

- Deterministic quality gates can count citations, stale citations, unsupported
  claims, and abstention mismatches, but they do not prove that citations
  semantically support each claim.
- The real-provider Enterprise AI smoke passed after Stage 11 preflight repair
  feedback was hardened, but source discovery and fixture generation still have
  meaningful provider-driven variance.
- `doctor` warns when embeddings are not configured, yet operators do not get a
  concise statement of the actual retrieval mode they are relying on.
- The current product is useful for personal workflows, but repeated use needs
  clearer guidance on when an answer is merely cited, when it is semantically
  supported, and when retrieval is FTS-only.

## Product Shape

The default answer workflow remains provider-backed answer synthesis followed
by deterministic inspection:

```bash
almanac ask enterprise-ai "What should I check before rollout?" --save
almanac ask-suite enterprise-ai --json
almanac refresh run enterprise-ai --ask-suite --save
```

v0.10 adds an explicit semantic validation layer:

```bash
almanac ask-suite enterprise-ai --judge --json
almanac ask-replay enterprise-ai --fixture tests/ask.jsonl --judge --json
```

The judge should be opt-in because it requires a provider call. It should not
replace deterministic checks; it should add a separate verdict such as
`supported`, `unsupported`, `mixed`, or `uncertain` with claim-level reasons and
citations.

## Ask Entailment Judge

The judge validates final answer claims against the cited excerpts already
available in saved answer or replay output. It should:

- evaluate only the answer text and cited evidence supplied by artifacts,
- avoid fetching new sources,
- produce a structured verdict with claim-level support status,
- mark uncertain cases explicitly instead of guessing,
- integrate with `trace.quality` or a sibling `trace.entailment` section,
- keep replay and suite output stable enough for regression review.

Recommended output:

- `status`: `pass`, `fail`, or `warning`,
- `verdict`: `supported`, `unsupported`, `mixed`, or `uncertain`,
- `claimsChecked`,
- `unsupportedClaims`,
- `uncertainClaims`,
- `provider`, `model`, and prompt version,
- compact per-claim evidence references.

## Compile Stability Controls

Compile stability should improve without freezing useful source discovery.
v0.10 should focus on explicit controls and diagnostics:

- show source-set drift when rerunning Stage 2/3,
- preserve accepted source ids when an update reruns discovery,
- report why prior accepted sources were reused, dropped, or replaced,
- add clearer Stage 11 repair guidance for enum-like fields and deterministic
  fixture replacements,
- expose coverage-floor decisions in Stage 11 logs and artifacts.

Candidate workflow:

```bash
almanac update enterprise-ai \
  --from-stage 02b-source-discovery-evaluator \
  --no-bump

almanac sources enterprise-ai --json
```

The operator should be able to tell whether a compile changed because evidence
changed, discovery changed, or benchmark generation changed.

## Retrieval Defaults

Retrieval currently works without embeddings via SQLite FTS. Embeddings are
optional and can improve semantic recall when configured. v0.10 should make the
active mode obvious:

- `profile` should summarize retrieval mode: `fts-only`, `hybrid`, or
  `vector-configured-but-skipped`,
- `doctor` should distinguish "embeddings optional" from "semantic retrieval
  expected but missing",
- docs should state the recommended default: Voyage when `VOYAGE_API_KEY` is
  present, OpenAI only when explicitly selected, deterministic/local for tests
  and offline workflows,
- hybrid retrieval should continue to use RRF unless benchmarks show the need
  for tunable weighting.

This is primarily a readiness and defaults hardening pass, not a new retrieval
algorithm release.

## v0.10 RC Smoke Target

The release candidate should pass:

- static checks: `git diff --check`, `bun run typecheck`, `bun test`,
- sqlite-demo deterministic run, ask, replay, ask-suite, and refresh validation,
- sqlite-demo optional judge smoke with mock provider,
- Enterprise AI fresh compile benchmark at `--depth standard`,
- real-provider Enterprise AI ask with citations and quality pass,
- saved-answer replay pass,
- `ask-suite` pass with deterministic fixtures,
- optional judge pass or documented warning outcome,
- `profile` and `doctor` showing retrieval and answer readiness clearly.

## Open Questions

1. Should judge failures fail `ask-suite --judge` by default, or should
   `--judge-strict` be required for hard failures?
2. Should judge results be stored under `trace.quality.entailment` or as a
   sibling `trace.entailment` section?
3. Should Stage 2 source-set drift be recorded in `sources/` artifacts,
   `.compile/`, or both?
4. Should retrieval readiness treat FTS-only as fully ready for all domains, or
   should broad/semantic domains recommend embeddings more strongly?
5. Should v0.10 choose a package publishing path, or defer distribution until
   after answer trust and compile stability improve?
