# v0.17 Implementation Plan

Status: shipped in v0.17.0 on 2026-06-10.

v0.16 shipped Actionable Studio / Guided Operations: users can see structured
next actions, run provider-free bounded operations from the CLI or Studio, save
answer-readiness evidence, and keep provider-backed work as explicit CLI
handoff. That made Almanac more operationally useful for users who already
have an almanac.

The remaining product gap is the first useful personal almanac. A user can
prove the product with `sqlite-demo`, but getting from an empty root and a
natural-language goal to a useful, cited, replayable answer still requires too
much command knowledge and too many internal concepts: source, facts, fixtures,
runs, refresh evidence, and answer readiness.

The shipped theme is **Guided First Useful Almanac**:

- make the path from empty root to first useful answer explicit and short,
- turn "what should I do next?" into a guided flow instead of scattered command
  suggestions,
- help users provide the minimum viable scope and sources for a real almanac,
- make abstention recovery actionable instead of merely correct,
- promote a saved first answer into replayable answer checks with fewer manual
  steps,
- keep provider-backed work explicit and reviewable,
- preserve cite-or-abstain, freshness, artifact, and runtime contracts.

## Target Users

v0.17 focuses on users who want to create their first real almanac, not only
inspect or maintain an existing one:

- personal users who know the topic they care about but not the Almanac command
  graph,
- users who can provide a few trusted references but do not know how to turn
  them into a scoped compile command,
- users who try `ask`, get a valid abstention, and need to know what evidence
  is missing,
- Studio-first users who want a local guided surface before reading the docs,
- technical evaluators who need to see a real first-answer loop without
  learning sources, facts, fixtures, and artifacts upfront.

The target is still a local source-first product, not a hosted no-code app.
The goal is to make the first useful almanac feel guided, not magical.

## Goals

- Add a first-use route that distinguishes empty roots, demo-only roots,
  partial failed almanacs, and ready almanacs.
- Make `start "<goal>"` and Studio onboarding produce a concrete first-use
  checklist: goal, slug, scope, reference requirements, provider boundary, and
  next command.
- Add a user-facing first-use report that hides internal artifact names behind
  setup, checks, answer readiness, first answer, and replayable answer status.
- Make source requirements explicit: minimum source count, trusted-reference
  examples, accepted URL kinds, and what remains missing.
- Improve valid abstention output with recovery guidance: refine question, add
  source, run answer checks, save evidence, or promote a saved answer when
  appropriate.
- Add a guided path from saved first answer to replayable answer checks using
  existing ask-replay, ask-fixtures, ask-suite, and refresh evidence contracts.
- Extend Studio to surface first-use state and provider-free next steps before
  users understand the lifecycle.
- Keep provider-backed compile and real answer generation as CLI handoff until
  a later release defines a broader credential and confirmation model.
- Keep no-key demo and replay workflows working as deterministic smoke paths.

## Scope

### First-Use State

Introduce a derived first-use status that can be rendered by `start`, `status`,
`profile`, and Studio:

- empty root,
- demo available,
- planning-ready goal,
- source checklist incomplete,
- provider-ready compile handoff,
- compiled but answer-readiness incomplete,
- first answer saved,
- first answer replayable,
- maintainable.

This status should be derived from existing files and reports where possible.
It should not become a second persisted lifecycle model unless implementation
shows a concrete need.

### Natural-Language Setup Guidance

Improve `almanac start "<goal>"` so planning output answers:

- what almanac would be created,
- what the user needs to provide,
- which provider-backed step would happen,
- which command is safe to run now,
- which command is blocked and why,
- how to open Studio for the same guided path.

The planning path should remain non-mutating unless the user passes an explicit
apply flag and enough references are present.

### Source Checklist

Add a source checklist that is concrete enough for first-time users:

- trusted official docs or repositories,
- optional secondary articles or community references,
- index-only vs snapshot implications in user-facing language,
- minimum viable sources for the requested goal,
- rejected or missing sources with direct next action.

This should not replace source discovery or evaluator policy. It should expose
the minimum useful input that makes the existing compile pipeline more likely
to produce a useful first answer.

### Abstention Recovery

When answer mode abstains, output should explain what to do next without
undermining cite-or-abstain:

- no citations found,
- citations found but unsupported synthesis,
- stale or warm evidence,
- no answer fixtures,
- saved answer not replayed,
- answer replay passed but readiness evidence not saved.

Each case should map to a guided operation or CLI handoff.

### First Answer Promotion

Saved answer promotion should become a guided first-use flow:

1. run first answer,
2. replay saved answer,
3. add replayable saved answer to ask fixtures when appropriate,
4. run ask-suite,
5. save answer-readiness evidence,
6. show the almanac as answer-ready or clearly explain the remaining gap.

The flow should protect against promoting invalid abstentions or provider-only
answers that cannot replay deterministically.

### Studio Onboarding

Studio should become a useful first screen for:

- empty roots,
- demo creation guidance,
- natural-language setup handoff,
- existing partial almanacs,
- first-use status,
- safe provider-free guided operations.

For v0.17, Studio can remain local and mostly handoff-oriented for
provider-backed work. The key improvement is that users can understand the
first-use path without starting from the CLI docs.

## Non-goals

- No hosted dashboard, account system, cloud queue, or background worker.
- No arbitrary source editing UI.
- No browser-based full source/fact/fixture/artifact editor.
- No hidden provider calls from `start`, `status`, `profile`, Studio GET, or
  Studio page load.
- No autonomous source discovery from vague prompts without explicit provider
  boundary and user review.
- No provider-backed Studio execution for compile or real answer generation.
- No arbitrary shell execution from Studio.
- No relaxation of localhost-only Studio binding.
- No replacement of the generic runtime boundary (`listTools`, `execTool`,
  `listResources`, `readResource`).
- No attempt to guarantee that every first answer is cited; valid abstention
  remains a successful safety outcome.
- No new hosted scheduler or resident daemon.

## Lessons From v0.16

- Guided operations reduce command memorization once an almanac exists.
- Studio action execution is useful when operations are provider-free,
  bounded, and operation-id based.
- Users still need a clearer path before the first almanac exists.
- `abstained` is correct but still feels like failure unless the recovery path
  is immediate and concrete.
- Answer-readiness evidence is easier to understand when it is framed as
  "save proof that checks passed" rather than `refresh run --ask-suite --save`.
- Provider boundaries should remain explicit. Users trust the product more
  when it says which next step needs credentials instead of trying to be
  automatic.

## Product Shape

The v0.17 workflow should feel like this:

```bash
almanac start "Build an almanac for my production AI governance notes"
almanac studio
```

The user sees:

- a concise proposed almanac name and scope,
- a checklist of needed trusted references,
- whether provider credentials are needed,
- the next safe command or Studio action,
- what happens after compile,
- how to ask the first question,
- what to do if the first answer abstains,
- how to make the first answer replayable.

For an existing but not-yet-useful almanac:

```bash
almanac status my-almanac
almanac operations my-almanac
```

The product should recommend the next first-use operation: add references,
rerun compile from a failed stage, initialize answer fixtures, run ask-suite,
save readiness evidence, ask first question, replay saved answer, or promote a
saved answer.

## Release Gate

v0.17.0 was cut after this gate passed:

- source and linked CLI versions match,
- empty-root `start` and Studio first-use state work without provider keys,
- natural-language `start "<goal>"` produces a concrete first-use checklist,
- source checklist guidance is actionable and does not mutate by default,
- sqlite-demo can reach replayable answer checks through guided first-answer
  promotion without provider keys,
- valid abstention includes recovery guidance and remains quality pass when
  appropriate,
- Studio shows first-use state and still blocks provider-backed execution,
- Studio remains localhost-only and GET/page load remains read-only,
- Enterprise AI still passes benchmark and real-provider ask/replay smoke when
  credentials are intentionally available.

## Decisions To Revisit

- Whether Studio should be able to create the sqlite demo directly, or only
  show the command for v0.17.
- Whether first-use reports should be persisted as artifacts or remain derived
  from existing reports.
- Whether source checklist policy should be purely heuristic or partly driven
  by domain-analysis output.
- Whether a future release should allow provider-backed Studio execution behind
  explicit confirmation and credential boundary.
