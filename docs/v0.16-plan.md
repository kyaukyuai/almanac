# v0.16 Implementation Plan

Status: PR5 in progress after PR4 merge.

v0.15 shipped Guided Activation: users can see activation milestones,
suggested questions, first-answer guidance, saved answer replay prompts, and
Studio activation state. The post-release sanity check confirmed that the
no-key sqlite-demo path can move from demo creation to answer fixtures,
mock first answer, saved-run replay, and maintenance dry-run.

The remaining friction is operational. Almanac now tells users what to run, but
still asks them to copy several commands and understand why some passing checks
are not persisted as readiness evidence until a separate saved operation runs.
Studio is useful as a local read-only dashboard, but it cannot yet execute the
safe provider-free operations that it recommends.

The v0.16 theme is **Actionable Studio / Guided Operations**:

- make recommended next actions executable when they are provider-free and
  bounded,
- turn copied commands into structured guided operations with explicit safety
  metadata,
- let Studio run safe local operations without becoming a source editor or a
  hosted app,
- reduce the gap between "this check passed" and "this evidence is saved",
- keep provider-backed work as copyable CLI handoff until the user explicitly
  chooses to run it outside the read-only/safe-action boundary,
- preserve cite-or-abstain, freshness, artifact, and runtime contracts.

## Target Users

v0.16 focuses on users who understand the local product enough to trust it, but
do not want to memorize the lifecycle command graph:

- personal users maintaining one or more local almanacs,
- users who prefer Studio for orientation and CLI only for provider-backed
  work,
- users who need to rerun answer checks, saved-run replay, or maintenance
  dry-runs without learning internal artifact names,
- users who are blocked by "copy this next command" loops,
- power users who want a safer local operations surface for teammates.

The target is not a no-code hosted product. The target is a local product where
safe operations are one click or one guided command, and risky/provider-backed
operations remain explicit.

## Goals

- Define a shared guided operation model derived from existing status,
  activation, answer-readiness, replay, refresh, and maintenance state.
- Mark each operation with safety metadata: provider requirement, mutation
  level, writes artifacts or not, expected duration, and confirmation needs.
- Add a provider-free operation runner for bounded local actions:
  ask-suite, saved-run ask replay, benchmark rerun, refresh status/evidence
  save, maintenance dry-run, and inventory reload.
- Make answer-readiness evidence persistence an explicit guided operation so
  users do not have to infer `refresh run --ask-suite --save`.
- Add localhost-only Studio POST actions for provider-free guided operations.
- Add Studio result panels that show success/failure, saved artifact path,
  next operation, and copyable fallback command.
- Keep provider-backed compile, live search, embeddings, and real answer
  generation outside Studio execution for v0.16.
- Keep all operations deterministic enough to test without provider keys.

## Non-goals

- No hosted dashboard, account system, remote queue, or background service.
- No arbitrary shell execution from Studio.
- No provider-backed Studio action execution.
- No browser-based source, fact, fixture, or artifact editor.
- No hidden mutation from page load or status reads.
- No autonomous refresh scheduler beyond the existing handoff contracts.
- No natural-language autonomous agent that chooses and runs multiple steps.
- No relaxation of localhost-only Studio binding.
- No change to the generic runtime boundary (`listTools`, `execTool`,
  `listResources`, `readResource`).
- No replacement of existing CLI commands; guided operations wrap and reuse
  them.

## Lessons From v0.15

- Activation state works. It gives users a coherent path from validated to
  answer-ready, first-answer, replayable, and maintainable states.
- Copyable commands are better than hidden actions, but not enough once the
  recommended action is provider-free and bounded.
- `ask-suite` passing is not the same as persisted answer-readiness evidence.
  The product needs to present "run answer checks" and "save this readiness
  evidence" as a guided operation, not as an implementation detail.
- Studio is already valuable as a dashboard. The next useful step is safe
  local operation execution, not artifact editing.
- Real-provider answers can validly abstain. Guided operations should treat
  pass/fail/abstain evidence explicitly instead of assuming success means a
  cited answer.
- The strongest personal-use value is repeatable local maintenance: check,
  replay, refresh evidence, dry-run maintenance, and know exactly what changed.

## Product Shape

The v0.16 workflow should feel like this:

```bash
almanac status sqlite-demo
almanac studio
```

In Studio, the user sees:

- current activation milestone,
- recommended operation,
- whether the operation is safe to run locally,
- what it will read or write,
- a Run button for provider-free bounded operations,
- a copyable CLI command for provider-backed or unsupported operations,
- the saved result artifact and next operation after completion.

The CLI should expose the same operation model for users who do not use Studio:

```bash
almanac operations sqlite-demo
almanac operations run sqlite-demo <operation-id>
```

Exact command names can change during implementation, but the contract should
be stable: list the available guided operations, run one explicit operation,
record or return its result, and never call providers unless the operation says
so and the user explicitly opts in.

## Guided Operation Model

A guided operation should be a structured object, not only a command string.
Suggested fields:

| Field | Meaning |
| --- | --- |
| `id` | Stable operation id for the current status response |
| `label` | Human-readable action label |
| `description` | One-sentence effect summary |
| `category` | `validate`, `replay`, `refresh`, `maintain`, `handoff`, `inspect` |
| `providerRequired` | Whether provider credentials may be used |
| `mutation` | `none`, `artifact-write`, `almanac-write`, or `external` |
| `confirmation` | Whether Studio/CLI must ask before execution |
| `command` | Equivalent CLI command |
| `studioRunnable` | Whether Studio may execute it in v0.16 |
| `expectedArtifacts` | Artifact kinds or paths expected after success |
| `blockedReason` | Why the operation cannot currently run, if blocked |

The operation model should be derived from current state and should be
renderable by `status`, `profile`, Studio inventory/status APIs, and the CLI
operation list.

## Safe Studio Actions

For v0.16, Studio may execute only provider-free bounded actions:

- reload inventory/status,
- run benchmark for an existing almanac,
- run ask-suite for existing answer fixtures,
- save answer-readiness evidence through the existing refresh/ask-suite path,
- replay saved answer runs by label or latest saved answer,
- run maintenance dry-run,
- optionally save maintenance dry-run evidence if the existing maintain
  command supports it safely.

Studio must not:

- execute arbitrary command strings,
- call provider-backed answer generation,
- call source discovery or compile stages that need providers,
- write sources, facts, fixtures, registrations, or generated tool code,
- bind outside localhost,
- mutate on GET/page load.

POST endpoints should take operation ids and explicit input only. They should
return the same result envelope as CLI operations so tests can validate both
paths.

## Result Envelope

Every guided operation should return a compact result:

- operation id and label,
- status: `ok`, `attention`, `failed`, or `blocked`,
- exit code when it maps to an underlying CLI command,
- provider use: expected and actual,
- duration,
- artifacts written,
- next operation,
- user-facing summary,
- machine-readable reasons.

If an operation writes a `.runs` artifact, the status/profile/Studio surfaces
should immediately be able to cite it.

### PR3: Provider-Free Operation Runner

Add a CLI runner for bounded provider-free operations.

CLI surface:

- `almanac operations <id>` lists current guided operations.
- `almanac operations list <id>` is an explicit list alias.
- `almanac operations run <id> <operation-id>` executes one operation by its
  structured operation id.

Candidate operations:

- run benchmark,
- run ask-suite,
- save ask-suite readiness evidence,
- replay saved answers,
- run maintenance dry-run,
- reload/list inventory.

Acceptance:

- The runner refuses provider-required operations by default.
- It never shells out through arbitrary user-provided command strings.
- It returns a result envelope with artifacts and next operation.
- It can persist evidence where the underlying command already supports safe
  artifact writes.

Validation:

- focused operation-runner tests,
- sqlite-demo no-key smoke,
- `bun run typecheck`,
- `bun test`.

### PR4: Studio Action API

Expose guided operation execution through localhost-only Studio POST
endpoints.

API surface:

- `POST /api/operations/:almanacId/:operationId/run` executes one guided
  operation through the same provider-free runner used by
  `almanac operations run`.
- The response body is the structured operation result envelope.
- If the Studio server is embedded without an operation runner, POST returns
  `operation-runner-unavailable`.

Acceptance:

- Studio inventory/status APIs list operation ids and runnable state.
- POST action endpoint accepts an operation id and returns the operation result
  envelope.
- GET/page load remains read-only.
- Provider-required operations are blocked with a clear reason.
- Non-localhost bind protection remains enforced.

Validation:

- Studio API tests,
- localhost boundary tests,
- `bun run typecheck`,
- `bun test`.

### PR5: Studio Action UI

Add a minimal UI surface for safe operations.

Acceptance:

- Each almanac shows its recommended runnable operation.
- Safe operations have Run buttons with confirmation when they write artifacts.
- Provider-required operations show copyable commands instead of Run buttons.
- Results show status, artifact path, next operation, and fallback command.
- UI remains useful without JavaScript-heavy state or external assets.

Validation:

- HTML/API snapshot tests or focused integration tests,

## Release Gate

v0.16 should not release until these hold:

- source and linked CLI versions match,
- sqlite-demo can list and run safe guided operations without provider keys,
- answer-readiness evidence can be saved through a guided operation,
- Studio can execute at least one safe artifact-writing action and one
  read-only action,
- Studio blocks provider-required actions and arbitrary command execution,
- Studio remains localhost-only and GET/page load remains read-only,
- saved operation results are visible in status/profile/Studio immediately,
- Enterprise AI still passes benchmark and real-provider ask/replay smoke when
  credentials are intentionally available.

## Decisions For v0.16

- Prefer a small structured operation runner over adding a broad natural
  language agent.
- Prefer Studio execution only for provider-free bounded operations.
- Prefer explicit artifact-writing confirmations over hidden persistence.
- Keep provider-backed work copyable until a later release defines a safe
  credential and confirmation model.
- Keep operation result envelopes compatible with existing `.runs` artifacts
  instead of creating a second history model.
